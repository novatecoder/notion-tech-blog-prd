# ROADMAP — AI/LLM 기술 블로그 (Notion CMS)

> 개발 로드맵 · 버전 v1.0 · 작성일 2026-06-07  
> 짝 문서: [`docs/PRD.md`](PRD.md) — "무엇을" 만들지. 본 문서는 **"어떤 순서로"** 만들지.

## 개발 원칙 — 골격 → 공통 → 개별 기능

기능 단위(목록 → 상세 → 필터…)로 쪼개 만들면 페이즈마다 Notion fetch·타입·레이아웃을 중복 구현하게 된다. 그래서 **재사용되는 것을 먼저** 만든다: 프로젝트 골격을 세우고(Phase 1) → 모든 화면이 공유하는 데이터 레이어·타입·컴포넌트를 구축한 뒤(Phase 2) → 그 위에 개별 화면을 얹는다(Phase 3~4). 이렇게 하면 개별 기능 코드가 얇아지고 변경 비용이 낮아진다.

| Phase | 단계 | 한 줄 | 예상 |
|-------|------|-------|------|
| 1 | 프로젝트 초기 설정 (골격) | 구조·환경·Notion 연동 기반 | 1–2일 |
| 2 | 공통 모듈/컴포넌트 | 데이터 레이어·타입·UI 프리미티브 | 2–3일 |
| 3 | 핵심 기능 | 글 목록·글 상세·블록 렌더링 | 3–4일 |
| 4 | 추가 기능 | 카테고리 필터·태그·404 | 2–3일 |
| 5 | 최적화 및 배포 | ISR·반응형·Vercel | 1–2일 |

---

## Phase 1 — 프로젝트 초기 설정 (골격) · 1–2일

**작업**
- Next.js 15 (App Router) + TypeScript 스캐폴드
- Tailwind CSS · shadcn/ui · Lucide React · `@notionhq/client` 설치
- `.env.local` 구성 (`NOTION_TOKEN`, `NOTION_DATABASE_ID`) + `.gitignore` 확인
- Notion 준비: Integration 생성 → 블로그 DB 생성(PRD §4 스키마) → Integration에 DB 공유 → `NOTION_DATABASE_ID` 확보
- 기본 레이아웃 골격 (`app/layout.tsx`, 전역 스타일, 폰트)

**왜 이 순서인가**
견고한 기반 없이 기능부터 만들면 환경·연동을 매번 다시 손대게 된다. 빌드·연동·레이아웃이 서 있어야 이후 페이즈가 그 위에 얹힌다.

**완료 기준**
- [ ] `npm run dev`로 빈 페이지가 뜬다
- [ ] Notion Integration이 DB에 연결되고 토큰으로 query가 1건이라도 성공한다
- [ ] `.env.local`이 git에 올라가지 않는다 (토큰 미노출)

---

## Phase 2 — 공통 모듈/컴포넌트 · 2–3일

**작업**
- 데이터 레이어 `lib/notion.ts`
  - `getPublishedPosts()` — `Status=발행됨` 글 목록을 발행일 내림차순 query
  - `getPostBySlug(slug)` — 단건 + 본문 블록 fetch
  - 블록 → 렌더(마크다운/HTML) 변환 (`notion-to-md` 또는 커스텀 매퍼)
- 공통 타입 `types/post.ts` — `Post`, `Category`, `Tag` (Notion 속성 매핑)
- Notion 속성 이름 상수화 + 런타임 검증 (스키마 변경 방어)
- 공통 컴포넌트 — `Header`, `Footer`, `PostCard`, `CategoryBadge`, `TagList`

**왜 이 순서인가**
목록·상세·필터가 전부 같은 fetch 함수와 `Post` 타입, 같은 카드를 쓴다. 이 공통층을 먼저 고정해야 개별 화면이 로직을 중복하지 않는다. PRD가 경고한 rate limit·토큰 노출·스키마 변경 대응도 이 레이어에 한 번만 넣는다.

**완료 기준**
- [ ] `getPublishedPosts()`가 발행 글 배열을 반환한다 (초안 제외 확인)
- [ ] `getPostBySlug()`가 본문 블록을 가져온다
- [ ] `Post` 타입으로 컴포넌트가 타입 안전하게 데이터를 받는다
- [ ] 토큰 호출이 전부 서버 측(Server Component / lib)에서만 일어난다

## Phase 3 — 핵심 기능 (목록·상세) · 3–4일

**작업**
- 홈 글 목록 페이지 `/` — `getPublishedPosts()` → `PostCard` 그리드 (제목·요약·카테고리·태그·발행일)
- 글 상세 페이지 `/posts/[slug]` — `getPostBySlug()` → 블록 렌더링 + 메타
- 블록 렌더러: 문단·헤딩·리스트·코드·이미지 등 지원 블록 화이트리스트 + 미지원 graceful fallback

**왜 이 순서인가**
블로그의 본질 기능. Phase 2의 데이터 레이어·컴포넌트를 조립하기만 하면 되므로 화면 코드가 얇다.

**완료 기준**
- [ ] 홈에 발행 글이 발행일 내림차순으로 보인다
- [ ] 카드 클릭 → 상세로 이동, 본문 블록이 렌더된다
- [ ] 없는 slug는 404로 떨어진다

---

## Phase 4 — 추가 기능 (필터·태그) · 2–3일

**작업**
- 카테고리별 목록 `/category/[category]` + 홈 상단 카테고리 필터 UI
- 태그 표시 (카드·상세) — MVP는 표시까지
- `not-found` 페이지 (없는 slug/카테고리)

**왜 이 순서인가**
핵심 기능이 선 다음의 부가 가치. 공통 컴포넌트(필터·뱃지) 위에 얹는다.
> **post-MVP (이번 범위 밖)**: 전문 검색·페이지네이션·태그 필터·다국어·댓글·RSS·OG 이미지 자동화. PRD §6 비포함 항목과 일치.

**완료 기준**
- [ ] 카테고리 필터가 해당 카테고리 글만 보여준다
- [ ] 태그가 카드·상세에 노출된다
- [ ] 없는 카테고리는 404로 처리된다

---

## Phase 5 — 최적화 및 배포 · 1–2일

**작업**
- ISR `revalidate` 설정 (Notion 변경 반영 주기)
- 이미지 최적화 (`next/image`), 반응형 점검
- Vercel 연결 + 환경변수(`NOTION_TOKEN`·`NOTION_DATABASE_ID`) 등록 + 배포 확인

**왜 이 순서인가**
기능이 완성된 뒤 품질·운영을 올린다. 캐싱·이미지·반응형은 화면이 다 있어야 의미 있는 튜닝이다.

**완료 기준**
- [ ] Notion에서 글 수정 후 ISR 주기 내 사이트 반영
- [ ] 모바일·데스크톱 레이아웃이 깨지지 않는다
- [ ] Vercel 라이브 URL에서 목록·상세·필터가 동작한다
